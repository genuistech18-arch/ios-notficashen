# Project Prompt: Code-Based Notification System (Backend + Flutter App)

## 1. Project Overview

Build a **notification delivery system** composed of two main parts:

1. **Backend Service** — stores client identities (a code + FCM token pair), exposes an API for a third-party/external service to trigger notifications by code, resolves the code to the correct FCM token, sends a push notification via Firebase Cloud Messaging (FCM), and logs every notification with a read/unread status.
2. **Flutter Mobile App** — allows a user to "register" on the device using an existing code (no password, no account creation), and displays their personal notification history.

The backend **never generates or validates the business meaning of a code** — codes are created elsewhere (in another system) and are only *persisted* here alongside the device's FCM token. The backend's job is purely to link `code ⇄ FCM token` and to route incoming notification requests to the right device.

## 3. Backend Service — Detailed Requirements

### 3.1 Core Entities

**User / Client Record**
- `id` (internal primary key, UUID)
- `code` (string/number, minimum 4 digits, **not generated by this backend** — only received and stored)
- `fcm_token` (string, nullable until the app registers it, updatable — a user may reinstall or switch devices)
- `created_at`, `updated_at`

**Notification Record**
- `id` (UUID)
- `user_id` (foreign key → User/Client Record)
- `message` (text sent from the external service)
- `is_read` (boolean, default `false`)
- `sent_at` (timestamp)
- `read_at` (nullable timestamp, set when the user opens/marks it read)
- `delivery_status` (e.g. `sent`, `failed`, `no_token` — for observability)

### 3.2 API Endpoints

**A. Register / Link Code + FCM Token** *(called by the Flutter app)*
- `POST /api/v1/clients/register`
- Body: `{ "code": "1234", "fcm_token": "<token>" }`
- Behavior:
  - If the code does **not** exist in the database → reject with a clear error (e.g. `404 Code not found` or `400 Invalid code`), since the backend never creates codes.
  - If the code exists → upsert the `fcm_token` on that record (overwrite the previous token, since a user might reinstall the app or switch devices).
- Response: confirmation + minimal user record (no sensitive data).

> **Open design question to resolve during implementation:** since the backend "stores but never creates" codes, something must seed codes into the database initially (e.g. an internal admin API, a sync job from the system that owns code generation, or a manual import). This prompt assumes codes are pre-seeded by another internal process — clarify this data source before building.

**B. Incoming Notification Trigger** *(called by the external service — must be protected, e.g. API key / bearer token)*
- `POST /api/v1/notifications/send`
- Body: `{ "code": "1234", "message": "Your order is ready" }`
- Behavior:
  1. Look up the user by `code`.
  2. If not found or no `fcm_token` on file → log the attempt with `delivery_status = no_token` / `not_found` and return an appropriate response (do not throw an unhandled error).
  3. If found → send a push notification via FCM to the stored token.
  4. Persist a `Notification` record (message, timestamp, `is_read = false`, delivery status).
- Response: `{ "status": "sent" | "failed" | "no_token" }`

**C. Get Notification History** *(called by the Flutter app)*
- `GET /api/v1/clients/{code}/notifications`
- Returns the list of notifications for that user, newest first, including `is_read` state.

**D. Mark Notification as Read**
- `PATCH /api/v1/notifications/{notification_id}/read`
- Sets `is_read = true`, `read_at = now()`.

### 3.3 FCM Integration
- Use the Firebase Admin SDK (server-side) to send push messages to a single device token.
- Handle FCM errors gracefully (invalid/expired token → mark token as stale, don't crash the request).
- Notification payload should include at least: title, body (the message text), and a data payload (e.g. `notification_id`) so the app can deep-link to the notifications screen and mark it read on open if desired.

### 3.4 Security Notes
- The "send notification" endpoint (used by the external service) must be authenticated (API key, signed request, or bearer token) since it is a server-to-server integration point — it should not be publicly callable.
- The "register" endpoint (used by the app) does not use a password, per the spec, but should still be rate-limited to prevent abuse/brute-forcing of codes.

## 4. Flutter App — Detailed Requirements

### 4.1 Screen 1 — Code Entry / Registration
- A single input field for the **code**.
- No password field.
- On submit:
  1. Retrieve the device's FCM token.
  2. Call `POST /api/v1/clients/register` with `{ code, fcm_token }`.
  3. On success: persist the code locally (secure local storage), and navigate to the Home screen.
  4. On failure (invalid/unknown code): show a clear inline error.

### 4.2 Alternative Entry — Deep Link Redirect
- Instead of manually typing the code, the app must support being opened via a deep link / universal link containing the code as a query parameter, e.g.:
  `myapp://open?code=1234` or `https://example.com/open?code=1234`
- On receiving this link, the app should:
  1. Extract `code` from the params.
  2. Automatically perform the same registration flow as the manual entry screen (fetch FCM token → call the register endpoint → store code locally).
  3. Skip the manual entry screen entirely if this flow succeeds.
- This should be implemented using a standard Flutter deep-linking package (e.g. `app_links` or `uni_links`) plus platform configuration for Android App Links / iOS Universal Links.

### 4.3 Screen 2 — Home Page
- Placeholder screen reserved for future functionality (per current scope, just needs a basic scaffold + navigation entry point to the Notifications screen).

### 4.4 Screen 3 — Notifications / Notification History
- Fetches and displays the list of notifications for the locally stored code via `GET /api/v1/clients/{code}/notifications`.
- Each item shows the message text, timestamp, and read/unread visual state (e.g. bold/dot indicator for unread).
- Tapping a notification calls `PATCH /api/v1/notifications/{id}/read` and updates local state.
- Should handle push notifications received while the app is in foreground/background/terminated (via `firebase_messaging`), updating the list accordingly.

### 4.5 Local Storage
- Store the registered `code` locally on the device (e.g. via `shared_preferences` or `flutter_secure_storage`) so the user does not need to re-enter it on every app launch.
- On subsequent app launches, if a code already exists locally, skip the entry screen and go straight to Home.

## 5. Suggested Tech Stack

- **Flutter App:** Flutter (Dart), `firebase_messaging`, `shared_preferences` or `flutter_secure_storage`, `app_links`/`uni_links` for deep linking, a state management solution (e.g. `Provider`, `Riverpod`, or `Bloc`), `dio` or `http` for API calls.
- **Backend:** Any standard backend framework (Node.js/NestJS, Django/FastAPI, or Laravel — choose per team preference), PostgreSQL or MySQL for persistence, Firebase Admin SDK for FCM.

3. **Deep link domain/scheme** to register for Android App Links / iOS Universal Links.
4. Whether a single `code` can be linked to **multiple devices/FCM tokens** simultaneously, or strictly one active token per code (current spec implies the latter — token overwritten on each new registration).
